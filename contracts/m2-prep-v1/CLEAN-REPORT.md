# CLEAN-REPORT：清理结果报告修正（M2 准备）

2026-10-27，总控（Claude）。修正 [CLEAN-HARDENING](../hardening-v1/CLEAN-HARDENING.md) 第 4 节第 7、8 步与 [CLEAN](../checkup-v1/CLEAN.md) 的 `bytes_freed` 算法，并取代 G1 补单 01 第 4、6 条、补单 02 第 4 条里与本文冲突的规则。冲突时以本文为准。

背景：G1 第三轮验收后，独立审查与总控竞态用例找出几处“删除过程中被别的程序改动时，报告的结果与实际不符”。它们都不会误删，但 M2 打开清理后，用户看到的“释放了多少”“失败几项”必须是真的。见 [G1 收单验收](../../docs/acceptance/wave4/controller/WATER-W4-G1-REVIEW-20261027.md)第三轮。

删除方式、句柄打开、复核、停止规则一律不变。本文只改**怎么判定结果、怎么计数、怎么算释放字节**。

## 1. 条目本身在删除开始前不在了或被换了

删除第一步相对父目录打开条目本身时：

| 情形 | 现在 | 改为 |
|---|---|---|
| 返回错误 2 或 3（条目已不在原名下） | 什么都不删、不计失败；残余为 0，报 `deleted`，`bytes_freed` = 全部 | 本项 `skipped`，原因 `gone`；`bytes_freed` 0，`failed_entries` 0 |
| 打开成功，但 FileId 不等于快照里的条目本身（原名下换成了别的对象） | 计 1 个失败并停止；残余按 `bytes_before`，报 `failed` | 本项 `skipped`，原因 `changed`；`bytes_freed` 0，`failed_entries` 0 |

两种情形都是“快照之后条目被移走或替换”，本次没有动它，所以不算失败，也没有释放。

## 2. 统计残余时条目不在了或被换了

删除已经开始、做过一部分之后，第 8 步统计残余时，原名下没有条目（错误 2、3），或者 FileId 不等于快照里的条目本身：
- 若本次运行**成功给条目本身设置了删除标记** → 原条目确已删除，残余 0。
- 否则 → 原条目被别人移走或替换，本次无法统计它还剩多少：残余按 `bytes_before` 计，不报 `deleted`，不额外计失败。

这把补单 02 第 4 条（只管“换成别的对象”）推广到“原名下没有了”。

## 3. 每个留下的对象只计一次失败

`failed_entries` 表示“本该删、但因为失败或被拒而留下的对象”的个数。一个对象留下，它的各级上级目录也因此删不掉，**上级目录不再重复计数**。

做法：删除过程中记住哪些快照项已经“有了交代”：
- 本身计过 1 个失败的项（删除失败、复核不符被拒、对象被换）；
- 因为里面还有东西而删不掉、但剩下的东西全都有交代的目录（见下）。

一个目录设删除标记失败时，用它自己的句柄再枚举一次：

| 剩下的内容 | 计数 |
|---|---|
| 至少一项，且每一项要么名字不在快照里（快照之后才出现），要么是已有交代的快照项 | 不计；本目录也记为已有交代 |
| 有任何一项是没有交代的快照项 | 计 1 |
| 为空，或再枚举失败 | 计 1（同补单 02 第 3 条） |

例：快照里有 `a\b\`，之后 `a\b\new.txt` 出现。`b` 删不掉，不计且有交代；`a` 删不掉、只剩有交代的 `b`，也不计；条目本身同理。全项 `failed_entries` 为 0，状态按残余判 `partial`。

例：快照里的文件 `a\x.bin` 被替换，计 1；`a` 与条目本身因它删不掉，不再计。全项为 1。

## 4. 快照查找忽略大小写

删除时按相对名在快照里查找：
1. 先精确匹配；
2. 找不到时，再按“忽略大小写”匹配：逐个字符做 Unicode 简单大写映射后比较。

匹配到的项，一律按“名字在快照里”处理：
- FileId 相同：同一对象只改了大小写，照常删除；
- FileId 不同：对象被换，按第 7 步与补单 02 第 1 条处理，快照项是目录就停止本项。

这样“计划里的目录被换成只差大小写的同名文件”不会被当成快照之后才出现的新项。Windows 默认目录不区分大小写；在区分大小写的目录里，这条可能多算一次“被换”，只会更保守。

## 5. 释放字节

```text
本次删掉了至少一个对象： bytes_freed = max(0, bytes_before − 残余)
本次一个都没删掉：       bytes_freed = 0
```

例如条目本身打不开、或全程被拒，`removed` 为 0，即使别的程序同时清空了文件、残余变小，也不算 Water 释放的。

## 6. 不变

- 删除方式、句柄、链接与重解析点规则、停止规则、守卫与保护路径、枚举结束判定；
- 公开 API、计划与报告的 JSON 字段；
- `deleted` 仍然只在残余确定为 0 时报告；残余未知一律按 `bytes_before`，计 1 个失败（补单 01 第 3 条）。
