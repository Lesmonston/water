## 1. 整组、整行“以后都跳过”（P2 服务、P3 宿主、P4 界面）

### 1.1 新命令 `skip_unit_add`

- 参数 `{conclusionVersion, unitId}`，两个都是字符串，键恰好这两个。
- `conclusionVersion` 不是当前结论的版本：`stale`。
- `unitId` 只能是下面之一，否则 `invalid`：
  - 当前结论里某张卡的 `card_id`，且这张卡的 `menu` 里有 `skip`（第 1.4 节）；
  - 当前结论里某个组在 `group_detail` 中给出的行，且这一行的 `skip` 为 `"unit"`（第 1.4 节）。
- 返回 `Locations`，和 `skip_add` 一样。
- `busy` 时（体检或清理在跑）返回 `busy`，和 `skip_add` 一样。

### 1.2 记下什么

| 点的是 | 新增的条目 |
|---|---|
| 单个组的卡（`kind` 为 group、leak、session、declaration） | `group`：这个组 |
| 合并卡（`m:`） | 卡里每个组各一条 `group` |
| 合并卡抽屉里的一行（`row_id` 就是组 ID） | `group`：这个组 |
| 抽屉的“同模板”行（`r:`，按 `t` 生成） | `template`：组 ID + 模板（`Item.template` 原样） |
| 抽屉的“同一父目录”行（`r:`，按 `d` 生成） | `folder`：组 ID + 父目录（原样大小写，比较时不分大小写） |
| 抽屉的“其它 N 项”行 | 不能跳过（`skip` 为 null） |
| 不超过 8 项时的一项一行（`row_id` 是条目 ID） | 照旧走 `skip_add {itemId}`，`kind` 为 `path` |

- **一次点击原子**：要新增的条目里，和已有条目**完全相同**的（同 `kind`、同组 ID、同模板或同目录，不分大小写）不重复记；其余的加上已有条数超过 64 时整次返回 `invalid`，一条都不写。全部已存在时原样返回 `Locations`，和 `skip_add` 一样把计划标为过期。
- **立刻生效**：写入设置后，最新一次体检里符合第 1.3 节的可清项马上改为不可清，原因 `user_skipped`，`reason_zh` 为“已设为以后都跳过”，结论版本加一，过期原因“跳过名单变了”（IPC-M35 已有）。照 SERVICE-M3C-ADD-01 对 `skip_add` 的做法。

### 1.3 以后每次体检怎么认

扫描结束、生成视图之前（照 SERVICE-M3C 第 5 节的位置）：

| `kind` | 条目改为不可清的条件 |
|---|---|
| `path`（已有） | 路径与记录完全相同（不分大小写），不连带上下级 |
| `group` | `item.group_id` 等于记录的组 ID |
| `template` | `item.group_id` 等于记录的组 ID，且 `item.template` 等于记录的模板 |
| `folder` | `item.group_id` 等于记录的组 ID，且条目路径的父目录等于记录的目录（不分大小写） |

- 只改原本可清的条目；受保护、仅供参考的不动。
- **新长出来的成员也算**：`group`、`template`、`folder` 认的是组与模板或目录，不是当时的路径。
- 一个泄漏簇的成员全部被跳过时，这个簇不出卡片，也不出线索。

### 1.4 卡片与抽屉怎么标

- **卡片 `menu`**：有 `skip` 的条件改为：卡的 `kind` 是 group、leak、session、declaration，所在组是可清级别，且至少有一项可清。`unfinished`（“上次没清完”）卡**没有** `skip`。合并卡照它包含的组判断，任一个组满足就有。
- **抽屉行**（`group_detail` 的 `rows[]`）新增键 `skip`，取值：
  - `"item"`：一项一行，`row_id` 是条目 ID，界面发 `skip_add {itemId: row_id}`；
  - `"unit"`：同模板行、同父目录行、合并卡抽屉里的组行，界面发 `skip_unit_add {conclusionVersion, unitId: row_id}`；
  - `null`：“其它 N 项”行；所在组不可清；行内没有可清项。

### 1.5 设置与 `Locations`

- 设置版本 `water.settings.v3` → `water.settings.v4`；读 v1～v3 时 `skipped` 的旧条目都按 `path` 处理。写回时一律 v4。
- `skipped` 每条：`{skip_id, kind, path|null, group_id|null, template|null, folder|null, title_zh, added_at}`。
  - `path` 只在 `kind` 为 `path` 时有值；
  - `group_id` 在其余三种时有值；`template`、`folder` 各在自己那种时有值；
  - `title_zh`：添加时就定下的说明，存进设置，以后不重算：
    - `path`：路径本身；
    - `group`：“<组标题> · <位置名>”，如“Python 工具缓存 · D 盘”；位置名取所在位置的显示名；
    - `template`：“<模板的显示标签> · <组标题>”，显示标签同抽屉行（SERVICE-M35 第 5.7 节，如 `verify-******`）；
    - `folder`：“<父目录名> 里的 <组标题>”。
  - `skip_id` 仍为 `s-` 加 6 位序号，与 `path` 条目共用一个序列。
- `Locations.skipped` 每条：`{skip_id, kind, display_zh, display_path|null, added_at}`。`display_zh` 为 `title_zh`；`display_path` 只在 `path` 时有值（与原来相同）。按 `added_at` 升序（原规则）。
- `skip_remove {skipId}` 对四种都适用，规则不变。

### 1.6 宿主（P3）

- 新命令 `skip_unit_add(conclusion_version: String, unit_id: String)`，转发 `{"conclusionVersion": ..., "unitId": ...}`。前端键 `conclusionVersion`、`unitId`。
- 宿主不校验内容。

### 1.7 界面（P4）

- **判断卡“⋯”**：`menu` 有 `skip` 时显示“以后都跳过”，点后发 `skip_unit_add {conclusionVersion: 当前结论的 version, unitId: card_id}`；成功后重读结论。M6 补单 02 “卡片忽略 `skip`”那条作废。
- **抽屉行“⋯”**：按行的 `skip`：`"item"` 发 `skip_add {itemId: row_id}`，`"unit"` 发 `skip_unit_add`，`null` 不显示“以后都跳过”。展开后的单项照旧发 `skip_add {itemId}`。
- **跳过名单页**（`settings/skip`）：每条显示 `display_zh` 与加入日期，旁边“移除”。不另加按类别的标签。
- 不加新按钮；不弹二次确认（名单里随时能移除）。

## 2. 关于、诊断与第一次打开（P2 服务、P3 宿主、P4 界面）

### 2.1 `app_info`（P3，宿主自己答，不经服务）

返回 `{name:"Flick", version, license, homepage}`：
- `version`：宿主包的 `CARGO_PKG_VERSION`；
- `license`：`"MIT OR Apache-2.0"`；
- `homepage`：`"https://github.com/Lesmonston/flick"`。

### 2.2 `diagnostics_get`（P2 服务；P3 转发 `{}`）

返回只含计数、状态与错误码的对象，**不得含任何路径、文件或文件夹名、组 ID、条目 ID、用户名**：

```text
{diagnostics_version:"flick.diagnostics.v1",
 service_version,                                   // 服务包的 CARGO_PKG_VERSION
 settings:{settings_version, categories_on, categories_off, custom_roots,
           skipped:{path, group, template, folder}, session_cleanup_on, trusted_declarations},
 last_scan:null|{status, duration_ms, scope:{drives, folders, common},
                 groups, items, eligible_items, levels:{recommended, confirm, advisory, protected},
                 issues:{<code>: count}},               // code 是扫描的问题码，如 access_denied
 last_clean:null|{status, freed_bytes, items:{<status>: count}, skip_reasons:{<reason>: count},
                  quarantine_batches, journal_error:bool},
 quarantine:{batches, bytes},
 store:{scans, snapshots, plans, cleans, quarantine, events, dedupes}}
```

数字一律十进制字符串或整数，照 IPC-M35 的通用约定（字节为字符串，计数为整数）。

### 2.3 界面（P4）

- **“关于”页**（`settings/about`，已有）加三行：“Flick <version>”“许可证 <license>”“项目地址 <homepage>”。项目地址旁一个“复制”。
- 同页加“复制诊断信息”：复制一段多行文本，第一行“Flick 诊断信息”，之后是 `JSON.stringify({app: app_info, platform: navigator.userAgent, service: diagnostics_get}, null, 2)`。复制方式与“复制线索给 agent”相同。
- **第一次打开**：`localStorage` 里没有 `flick.intro.v1` 时，在首页之前显示一页说明：
  - 标题“Flick 怎么用”；
  - 三行：“体检只读：只看名字、大小和时间，不读文件内容。”“清什么由你点：推荐的直接清，要确认的先放进隔离区。”“隔离区里的随时能还原，永久删除前会再问一次。”；
  - 一个主按钮“开始”，点后写入 `flick.intro.v1` 并进首页。
  - 读写 `localStorage` 出错时不显示这一页（不挡用户）。

## 3. 执行器：写日志失败时照样交回报告（P1）

M4 中等遗留。适用 `execute` 与 `quarantine`；`purge`、`restore` 不在本单。

- **还没动任何东西**时（第一条 intent 就写不进）：照旧返回 `Err(CleanError::Journal)`。
- **已经动过至少一项之后**，任何一行日志写不进（intent、result 或结尾一行）：
  1. 不再动后面的任何一项（日志写不进就不能先记后做，W-F12）；
  2. 这一项若还没动：报为跳过，原因 `JournalFailed`；已经动了的照实际结果报；
  3. 后面没处理的项都报为跳过，原因 `JournalFailed`；
  4. `status` 为 `Stopped`；`journal_error` 为 `Some("journal write failed")`；
  5. 返回 `Ok(report)`，`freed_bytes` / `moved_bytes` 只算真的做了的。
- 这条之外的行为都不变。

另：`examples/real_smoke.rs` 列固定盘时启动的 `powershell.exe`，改用 `%SystemRoot%\System32\WindowsPowerShell\v1.0\powershell.exe` 的绝对路径（N3 低）。

## 4. 服务的收尾（P2）

### 4.1 首页重复计嵌套条目

`conclusion_get` 的 `plan`（`bytes`、`chosen` 与 `irreversible` 两块的体量、`item_count`、`by_drive`）只算去嵌套后的条目：用与 `clean_prepare` 相同的“只留最外层”（W11-N8 第 1.8 节），是否算进“你选的”看外层那条。

### 4.2 抽屉与计划一致

推荐组的抽屉行里，“上次没清完”的条目若不进计划，就不显示为已包含（M7 低）。

### 4.3 趋势页从没比较过的泄漏簇

`trends.clusters[].state` 新增 `"new"`：簇所在组在 `growth` 里没有记录、没被标记已修、不是“疑似”时。此时 `rate_zh` 为“最近 14 天新增 k 个”或“最近 14 天没有新增”，与首页卡片同一个算法（W11-N8 第 1.5 节）。`growing`、`stopped`、`suspected` 的条件不变。

### 4.4 写日志失败与隔离报错时的清理记录

- 执行器返回的报告带 `journal_error` 时：照常保存清理记录；`CleanResultView` 新增 `journal_note_zh`：“清理日志没写全，后面的 N 项没有清”（N 为 `JournalFailed` 的项数）。没有时为 `null`。
- 跳过原因 `JournalFailed` 在各组的说明里单独一条：“N 项因日志写不进去未处理”。
- **W11-N8 第 1.9 节**：直接删除已完成、某个盘的隔离批次随后返回错误时，**照常保存这次清理记录**：直接删除的结果照实写；出错那批的组 `status` 为 `failed`，说明“没能放进隔离区：<原因>”；`clean_result` 能读到这条记录。原来整次返回错误、记录不存的做法作废。
- 还没动任何东西就写不进日志（执行器返回 `Err(Journal)`）时，照旧返回 `JOURNAL_MESSAGE`。

### 4.5 隔离区刷新的顺序

`quarantine.rs` 的 `refresh_with`：先检查根是不是普通目录，过了才记进 `seen_roots`（W11-N8 低）。
