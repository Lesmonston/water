## 独立代码审查

每张票一个只读审查代理，只给代码与对应 SPEC、原契约，不给总控的结论。

### G2：没有高、中级问题

审查确认：
- `call` 与两条后台线程都整体受保护；
- 锁中毒可恢复；
- 只有本进程完成的扫描能做清理来源，读回的计划一律 stale，执行只用内存里的计划；
- 整理只删符合格式的普通文件与超出上限的旧记录，不进联接、不递归；
- 规范路径在添加与读回设置时都检查；
- 第 6、7 节的规则与文字逐字符合；
- 旧断言只改了 Chrome 那一条；
- 没有新依赖、unsafe、进程、联网或公开接口。

低级观察，移交后续收尾：
1. 扫描记录先写盘、后进锁内更新。若锁内那段 panic（实际难以触发），磁盘上会留一份 completed 记录，重启后显示为上次体检（只显示，不可作为清理来源）。
2. `clean::start` 先把 busy 设为 cleaning，再按键取 `details`。若该处 panic，busy 会卡住；现在 prepare 已用同样的键取过，触发不到。
3. 读回的计划若已用过或令牌不对，返回 invalid 而不是 stale；仍然不可执行。
4. 规范路径比较取代了原来的文本比较，而不是两者都查。若某个已知目录本身是联接，它的上级文件夹现在可以加为自定义位置；扫描与清理都不进联接，不会造成危害。以后可以两种比较都做。
5. `WindowsPlatform` 的进程快照锁不恢复中毒：一旦中毒，占用检查永久为“无法确认”，安全但退化。
6. `canonical()` 对 UNC 形式的去前缀不完整；自定义位置必须是盘符路径，没有实际影响。
7. 测试缺口：
   - 清理线程没有注入 panic；
   - 预算用尽一支未测（总控 x7 存活）；
   - 整理上限的 70 个 ID 时间戳相同，去掉排序也能通过；
   - 锁中毒那段失败信息缺标记（总控 x1）。
