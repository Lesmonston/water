## 查出的问题（都已修好）

1. **宿主的 `Cargo.lock` 没跟上 M7（产品，`936cc516`）。** M7 给服务加了三个本地包（项目声明、查重、已安装程序），宿主依赖服务，但宿主的锁文件没更新。主线上用 `--locked` 编宿主会要求重写锁文件。第一轮里宿主的 lock 模式在树 B 自动补上了，非 final 的检查不要求树干净，所以 check、test 都过了，直到整机检查（final）因“树不干净”拒绝开窗才暴露。改动只加三个本地包和它们在服务下的名字，没有外部新包、没有版本变化。修好后两棵树快进到 `c1dd420c`，**十个部分全部重跑**；第一轮的日志留在 [round1/](integ7-20261107/controller/round1/)。
2. **检查器让多个包共用一个编译目录（总控脚本，`3330a0d4`）。** 每个包的真实冒烟都是名叫 `real_smoke` 的示例程序。树 A 里七个包共用 `.local/w2-target`，源码没变时 cargo 不重新链接，`cargo run --example real_smoke` 跑的是最后链接的那个程序：第一轮里进程这一部分打印的是执行器的计数，第二轮里六个部分打印的都是已安装程序的计数，检查器照样判通过。改成每个包一个子目录 `.local/w2-target/<包目录>` 后，七个部分的真实冒烟重跑，各自打印自己的结果（下表）。**以前的整合检查也用同一棵树 A，同样可能受影响**；第六次报告里的进程、规则、扫描数字各不相同、与包对得上，应当没有中招，但没有办法事后证明。
3. **整机观察脚本不会按开关按钮（总控脚本，`82d1951d`）。** v3 首页的位置按钮带 `aria-pressed`，在 UI 自动化里是开关按钮，没有“点击”接口。第一次开窗停在第 2 步（[证据](integ7-20261107/controller/native-attempt-1/)），窗口正常关闭，什么都没动。补上“没有点击接口就用切换接口”后重开，一次通过。

另外第一次跑服务测试时，`service_scan_views` 里 `skip_add` 超过 200 ms，只因计时失败，按用户 11-06 的规矩原样重跑通过；在 `c1dd420c` 上重跑时一次通过。
