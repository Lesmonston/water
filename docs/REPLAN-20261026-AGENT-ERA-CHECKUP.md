# Water 计划重订：对齐本机清理实战（2026-10-26，草案待拍板）

总控（Claude）起草。依据用户 2026-10-26 要求：先不安排后续任务，消化本机清理总结，再结合项目重订计划。**本文是提案，不改任何任务状态，不建工作树，不发票。** 拍板后再改 ROADMAP、MVP-REQUIREMENTS、ARCHITECTURE 并出波次。

## 0. 结论

Water 前 10 天建成了一套很严的只读底座（31 张票全部验收），但用户价值几乎为零：所有扫描结果都是“未知 / 受保护”，也没有任何清理出口。本机三次 C 盘告急证明，真正的痛点是**已知位置上的 agent 工具垃圾和持续泄漏**，而且靠“已知位置登记 + 前缀归类 + 增长对比 + 在用跳过 + 预览后由用户执行”就能安全解决。

建议把 M1 主线从“用户选一个项目目录做元数据观察”改为 **“Agent 时代开发机磁盘体检”（Windows 先行）**：自动看已知位置，告诉用户谁在占、谁在涨、哪些能放心清、哪些要确认，并给出可由用户本人运行的清理脚本。现有安全底座大部分复用，项目目录分析降为次要功能。

## 1. 本机清理实战说明了什么

来源：共享库 Skill `skills/agent-era-disk-junk-cleanup`；denglou 记忆 `c-drive-growth-and-f-cache`、`headless-chrome-profile-cleanup`、`taskstop-leaves-agent-children`、`jest-cache-holds-source-text`；denglou 10-23 交接；当时的 `scan_c.ps1`、`group_temp.ps1`、`cleanup_c_1023.ps1`（只读查阅）。

| 日期 | C 盘剩余 | 主要元凶 |
|---|---|---|
| 10-01 | 16.6 GB | pagefile 31 GB、jest 缓存 8.7 GB、AVD 9.9 GB、`.gradle` 5.2 GB、Codex 升级失败残留 4.4 GB、Chrome 端侧模型 4 GB |
| 10-07 | 23 GB | 会话 scratchpad +10 GB，其中 206 个 `hrender-*` 无头 Chrome profile 6 GB；jest +4.9 GB |
| 10-23 | 8.1 GB | 另一项目浏览器测试泄漏 `rb*-x-chrome-*` 约 1970 个 / 48 GB，约 17 GB/天；Codex staging 237 个 / 7 GB。清理后 67.1 GB |

六条可直接变成产品需求的结论：

1. **最值钱的是定位和归属，不是删除。** “Temp 有 48 GB”没用；“car op 的浏览器测试每天漏 17 GB”才有用。
2. **找泄漏要看增长，不看大小。** 按大小排序会被 AVD、模型这类一次性大块误导。
3. **前缀归类是关键手法。** 把目录名尾部随机码和数字归一化后分组，成百上千个同前缀且最新时间在刷新，就是正在泄漏。
4. **安全来自简单规则：** 已知位置 + 名字模式 + 年龄阈值 + 在用跳过 + 不跟联接 + 默认预览 + 用户本人执行 + 前后对比。三次清理都没有误删。
5. **有些东西不是垃圾。** 会话记录能续接和取证；连 jest 缓存都曾救回丢失源码。这和 Water“可重下不等于可回滚”“未知保护”的原则一致。
6. **清理只能止血，根治靠修生产者。** 工具应生成“去哪个仓库、哪个文件、在 close() 里删临时目录”的修复说明。

## 2. Water 现状对照

| 实战需求 | Water 已有 | 差距 |
|---|---|---|
| 扫已知位置（Temp、`~/.codex*`、`~/.claude`、npm-cache 等） | 只扫用户在原生对话框里选的一个目录 | 没有位置登记表；从未读过真实用户位置 |
| 大目录体量（单个 Temp 下 2000 个 profile、几十万文件） | 遍历上限深度 8、总条目 10000、每目录 256，逐条输出 | 需要只出汇总的大预算体量遍历 |
| 前缀归类、个数 / 体量 / 最早 / 最新 | 无 | 全新 |
| 增长对比、泄漏告警 | 无 | 需要快照存储与差分 |
| 归属到工具 / 项目 / 会话 | 无（全部 unknown） | 路径编码解析、进程命令行匹配 |
| 在用检测、孤儿进程 | 无 | 只读进程快照 |
| 四级安全分类 | 只有 protected / unknown | 规则驱动的分类 |
| 清理出口 | 无（M1 不许有删除接口） | 可先生成由用户运行的脚本 |
| 跳过联接、不读内容、脱敏导出、可取消 / partial | **已有且已验收** | 复用 |
| 桌面壳 | 静态 Tauri 窗口已验收 | 接线待做 |

## 5. 现有资产去留

- **复用：** A 契约里的未知保护和字节字符串约定；R 的句柄相对、不跟联接遍历思路；Q 脱敏导出；AC 桌面壳与导航、CSP 校验；AB/AD 的同意绑定与页面样式；B 规则包的数据加校验器写法。
- **降为次要：** AA/AB/AD 的“选项目目录 + 读 package.json 结构”流程保留为“项目目录体检”，暂不追加投入。
- **改设计：** 我上一轮草拟、尚未出票的桌面接线方案（把 AB 的 Node 校验搬到 Rust、再接 Tauri）不再按原样推进。新主线不需要原生选择器和子进程，可信宿主直接在进程内调用体检内核，接线明显更简单。
- **保留待用：** AE 的 macOS 研究留给 M3。

## 6. 安全边界的变化

这是方向调整里最需要用户拍板的一条：**新主线必须读本机真实位置的元数据**，而项目至今的规矩是“不扫 HOME、整盘或真实用户数据”。提案边界：

- 只读登记表列出的位置，根路径由可信宿主按系统已知目录解析，界面只能传组 ID，不能传路径。
- 只读名字、大小、时间、属性，不读任何文件内容。会话记录目录只计个数和体量，导出时目录名脱敏。
- 只读进程列表和命令行，用于在用判断与归属，不结束任何进程（M1）。
- 不跟随联接；联接只显示“指向哪里”。
- 未被登记表识别的目录只显示体量，归入“未识别”，默认不可清。
- 删除只在用户本人运行脚本（M1）或应用内逐次确认（M2）时发生。

## 7. 流程调整建议

前 31 张票的门很重：每波几百个冻结约束、多轮补单；AC 一个静态窗口用了 6 张补单。建议：

- **只读功能用轻门：** 一份 SPEC、一份测试清单、一个检查脚本；负控只砍承重逻辑（分类、在用跳过、联接跳过、根内路径）。不再为每波冻结全仓几百个文件。
- **执行 / 删除路径保留重门：** M2 起沿用现有的冻结、负控与独立复核。
- **体检不需要原生对话框，** 真实验收不再受窗口预算拖累。
- **Water 自身瘦身：** 已验收工作树的构建产物可重建，建议定一条保留规则（证据保留，构建产物可删）。删除由用户本人执行，总控只给脚本。
