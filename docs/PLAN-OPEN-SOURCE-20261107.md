## 3. 公开仓库：不能直接把现在的仓库设为公开

现在的私有仓库：
- 跟踪了约 8.8 万个文件，其中约 8.7 万个是 `docs/acceptance` 下的验收证据，打包后 402 MB；
- 约 1.8 万个文件里有本机用户名 `37310`，546 个里有 `mirasim`；
- 提交历史里的作者有两个个人 gmail 地址。

产品代码（`packages`、`apps`、`scripts`）里没有这些。

**推荐做法**：
- 新建一个公开仓库，只放产品代码、规则、用户文档与必要的契约，用一个干净的首个提交，不带历史；
- 现在的私有仓库照旧是工作仓库，派单、验收、交接都还在这里；
- 每次发布用一个导出脚本，从私有仓库生成公开仓库的内容，导出后自动扫一遍，不许出现用户名、私人路径和邮箱。

另一种做法是改写现有历史再公开：要清掉 8.7 万个证据文件和所有作者信息，工作量大，容易漏。

## 5. 为什么慢、怎么提速

### 5.1 原因

拿第十一波看：8 张单，15:45 出单，20:20 收口，约 4.5 小时。
- **分两批**：服务单要等执行器合入才能开工，第二批多等了约 2 小时。
- **验收太重**：每张单总控都新建一棵验收树全部重跑，还另做变异。轻门的单也重跑，一张二三十分钟。
- **一波一个主题**：单子都很小。第十一波主要是改名，草稿里的第十二波主要是跳过，看得到的变化少。
- **总控出单的疏漏要返工**：第十一波 N3 的前提错了；第十二波草稿里列了三条第十波 M10 早已修好的执行器问题。

### 5.2 做法

1. **每波一批出完，不再分两批**：跨目录的新接口（类型、命令名）由总控先写进基线，各单同时开工。
2. **每波 8～10 张单**：功能和收尾一起排。
3. **验收再减**：
   - 轻门只做审计、看执行者的回执与截图，不重建验收树；
   - 变异只给执行器和服务，各 3 条；
   - 整合时统一重跑全部测试，兜底。
4. **文件少写**：契约每波一份；计划直接写到单子能用，不另写派前回执；出单前先对照已合入的单，不列已修好的问题。
5. **整合一次跑完**：整合、release、冒烟、复验已经有现成脚本，接成一条命令，约半小时。
6. **执行者多开**：除了 astra、sol，小单可以给 grok 或别的执行者，同时开几个由你定。

按这个做，第十二波 8～10 张单的目标是一批出完、半天内收口。

## 6. 要你定的

1. **整体按第 4 节走**：第十二波照扩大后的范围，第十三波做公开仓库，然后发布 v0.1。
2. **提速做法照第 5.2 节**，特别是轻门不再重建验收树。
3. **同时开几个执行者**。
4. **跳过记什么**：推荐“这个位置上的这一类”，新长出来的也跳过。
5. 第十三波之前定：
   - **许可证**：推荐 `MIT OR Apache-2.0` 双许可（Rust 项目的常见做法），也可以只选其一，或选 GPL-3.0；
   - **公开方式**：推荐新建干净的公开仓库（第 3 节）；
   - **仓库名**：推荐 `flick`。
