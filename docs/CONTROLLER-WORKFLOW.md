# Water 总控与人工外贴工作流

版本：v1，2026-10-17。来源：用户本轮明确分工，以及 [denglou/car op只读调研](../research/CONTROLLER-WORKFLOW-STUDY.md)。实际在途票以本项目manifest/registry为准。

## 1. 角色与权限

| 角色 | 负责 | 边界 |
|---|---|---|
| 总控Codex | 需求澄清、架构、数据与模块契约、拆单、文件归属、依赖、验收设计、外贴指令、收单、复测、集成和状态交接 | 不自行消化普通实现单；实质产品修复回派。可写架构、工单及验收材料，判断和处理集成问题 |
| 用户 | 转贴总控给的短指令、安排外部IDE/模型、传回任务完成或受阻通知、产品与发布决策 | 不要求用户逐项检查代码、调试接口或手工解决Git冲突 |
| 外贴执行者 | 读指定工单，核对环境，在指定分支完成范围内实现、定向验证、必要负控、回执和提交 | 不擅改架构/冻结契约/检查工具，不合主线、不发布、不越界修别人的问题 |

总控默认不自动启动本地worker、内部实现子代理或第三方服务代替用户外贴。只读分析辅助如使用也不取得实现/发单权限。实际引擎和模型由用户安排，收到后如实记入台账，不预填或借用其他项目的模型安排。

## 2. 权威材料与冲突处理

用户明确要求优先；项目安全不变量和本流程为底线；具体工单及编号补充单约定范围；波次manifest记录基线/分支/清单；冻结契约定义接口。

若这些材料冲突，执行者不自行选一个继续：写明具体冲突交总控修订。补充单必须编号、绑定原单及基线，所有受影响票面/manifest同步；聊天里的一句临时说明不能静默改变契约。

模板在 [dispatch/templates](dispatch/README.md)，**含占位符的模板不能外贴执行**。现有W0/W1是阶段工单，不是已经准备好的外贴票。

## 3. 总控出票前检查

1. 明确可观察行为、安全不变量、验收样本；根因推测标明待证实，不把猜测写成事实。
2. 先完成本轮架构与契约。生产类型可以由执行者按冻结规格实现，但字段/状态/错误语义不能自行改；共享契约与注册入口有唯一负责人。
3. 按可独立实现、编译和验收的边界切单；列出前置、并行冲突和改动白名单。需要同一文件的两单串行，或明确不相交的追加位置及总控整合要求。
4. 在water内准备独立工作树、分支、精确基线与本票目录；一槽一次只属于一个执行对话。不得借用denglou/car op槽位。
5. 核实工单、必读材料和回执父目录真实存在；若工单不在执行树，写明权威票面路径和只复制票面的规则，不能merge主线取票。
6. 核实开发工具与定向命令，跑票面允许的基线，记录当前已知失败。需要安装/锁文件变化时点名唯一环境单；普通执行者不得自行升级依赖或修改全局环境。
7. 每张票指定测试文件、执行器、日志目录和资源上限；清单为空必须拒绝运行。不得引用尚不存在的Water测试helper或冒充它已限制权限。
8. 冻结本轮manifest，登记槽位、分支、SHA、依赖、共享文件、证据与报告路径。达到全部条件才标READY并给用户外贴句。

默认先开少量独立票，不为了并行把强依赖拆成无法独立编译的碎片。后续波次可起草，但本轮未收口、必要前置未验收时不派出。

## 4. 用户实际外贴的内容

标准形态仅一行：

```text
请读取 <已经存在且可访问的具体工单绝对路径>，开始执行任务。
```

工作树、分支、基线、范围、必读、检查和回执都在票面。总控给用户时可在句子外标清票号/主题，不能让用户自己补路径、挑基线或拼执行命令。

READY只表示总控已准备好，不表示用户已转贴。得到用户已贴的明确消息或执行者启动证据才记DISPATCHED/RUNNING；不靠等待时间推断有人在工作。共享本机目录不可访问的执行环境，须另发可复现材料包和明确交回方式，不能假设远端模型能读本机路径。

## 5. 执行纪律

- 开工先核对绝对工作树、分支、基线祖先关系和已有改动。初次启动与补单续做分别说明允许状态；不对即停，不自行换分支或重置。
- 只改票面列出的文件；需要接口变更、额外文件、依赖或检查调整时交受阻回执。原有失败、其他槽位文件、共享Vault和research/upstream只读。
- 禁止通用递归删除、清缓存、git clean、hard reset、全树还原、覆盖/清除他人改动、批量git add；不得读取真实凭证或操作用户真实数据。项目的测试夹具回收只允许票面列明且有边界校验的机制，不授权手工清目录。
- 禁止push、merge、rebase、cherry-pick别人的任务、自行部署和签名采购；执行者只提交自己的分支与显式文件。
- 只跑本票定向检查，不跑整仓全量/coverage/watch或并行启动多个重负载检查；使用独立fixture与构建输出，资源协调按Water自己的已实现工具和票面执行。
- 外部执行者默认不再分包给写代码的子代理/CLI。只读辅助若票面允许，必须回执记录，不能让多个写入者共用同一树。
- 不为过检查删测试、skip、降断言、放宽超时或改检查工具。预先批准的行为/清单变更逐项写原断言、新断言及理由；未列的语义冲突报告总控。

这些规则约束开发行为，不等于Water产品实现了文件系统安全；产品清理仍按架构及后续执行器工单独立验收。

## 6. 验证与回执

对有行为变化的实现，用能失败的目标测试先证明问题，再实现。安全关键路径配反向验证：临时改坏真正逻辑，确认指定断言失败，按原字节恢复，核对哈希，再跑最终清单。编译失败、缺文件、超时或测试专用开关引起的红不能算有效负控。文档等低影响任务不机械要求负控。

至少一条关键用例走实际组装/公开入口，不能在测试里补上运行时缺失的配置。Water尤其关注scope、适配器、保护策略、容量汇总与IPC真实接线。测试不写真实HOME，不用用户项目当破坏性夹具。

执行者回执必须包含：票号/补单、基线、工作树/分支、实现提交SHA、实际改动、需求逐项对照、测试命令与退出码/汇总/日志、有效负控及恢复、越界申请/假设/未验证平台、剩余问题和实际模型。绑定测试过的实现提交；后加报告提交不允许夹带未验证产品变更。

完成后在本分支提交代码与报告。受阻也保存范围内现场，报告具体原因与最小补充需求；不问用户放宽权限、不让另一人悄悄接管脏树。回执路径与提交核实后停止修改。

对话只需一句定位通知，报告第一行同句：

```text
<票号>[ 补充单N] 任务已完成，任务报告在 <绝对路径>
<票号>[ 补充单N] 任务受阻，任务报告在 <绝对路径>
```

执行者写“完成”只使任务进入SUBMITTED，不能自行标总控验收通过。

## 7. 总控收单、补单与集成

1. 先定位回执和实现SHA，核对branch/base、干净状态、未提交残项及实际diff；只采信可复核证据。
2. 核对文件范围、接口、依赖、保护条件、测试改动和日志；复跑关键定向门，并用独立验收夹具/反向样本验证需求。
3. 失败按原因分清：票面漏项、环境缺失、实现缺陷、测试无效或确未验证；总控改规划/契约或发编号补充单，功能修复仍由外贴执行者完成。
4. 单票通过后在water内的集成树整合。冲突按冻结语义判断；需要实质实现修正则回派，不静默吞掉。合并无冲突也核对注册项/计数/默认值/配置与版本契约。
5. 总控在集成提交上跑适当整体门与真实接线检查；Windows、macOS分别记录，未做的平台保持未验证。大门按资源预算串行安排，不长期占满执行者名额。
6. 通过后再更新main、台账和状态。验收后若再改产品代码，受影响检查重跑；单票绿、集成绿、平台绿、可发布和已发布分别记录。

总控验收不等于额外授权产品清理真实用户数据。任何首次真实数据动作仍需具体范围与已有用户授权；未授权时在隔离fixture内验证。

## 8. 状态与交接

状态主线：DRAFT → READY → DISPATCHED → RUNNING → SUBMITTED → IN_REVIEW → ACCEPTED → INTEGRATED → VERIFIED → CLOSED。受阻使用BLOCKED；返工使用CHANGES_REQUESTED并绑定补单。ACCEPTED只表示单票通过，不等于整体交付。

槽位表、任务manifest、工单和回执共同记录事实；总控维护状态，执行者不能编辑主线台账。接手优先读STATUS、架构/契约、本轮manifest和最后验收记录，不依赖聊天记忆。

每轮结束记录：已完成、实际集成SHA、跑过与没跑过的检查、已知失败、在途票/槽位占用及下一步。保留在water内，不写其他项目或共享Vault。
