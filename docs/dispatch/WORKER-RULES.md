# Water 执行者通用规则

2026-11-07，总控（Claude）。从第十一波起，每一波的执行者规则都以本文件为准，波次规则只补本波特有的内容：单号与目录表、检查入口、门、真实数据范围。两者冲突时以工单为准，其次是波次规则，再次是本文件。

本版在[第十波规则](W10-M35-WORKER-RULES.md)的基础上改了“什么时候停下”：第十波 20 张补单里约 8 张没有任何产品要改，只是执行者按规则停下来等许可（[复盘](../acceptance/wave10/controller/WATER-W10-REVIEW-20261105.md)第 15 节）。现在的原则是：**能照规则自己做完的就做完，回执里写清楚；只有下面列出的几种情况才受阻。**

## 1. 开工

1. 只认工单里的绝对路径。先读本文件、波次规则、工单，以及工单列出的 SPEC 与契约。
2. 在工单指定的工作树根目录跑工单给的 baseline 命令，不要 cd 到别处。baseline 只证明环境与输入就绪；失败就停下写受阻回执。
3. 离线依赖由检查器复制，不要自己复制或下载。
4. 同一工作树同时只能有一个执行者。开工时 `git status` 必须是工单写的状态；不是就停下，不要接管别人的未提交改动。

## 2. 写代码

- 只改工单白名单里的文件。别的单的目录、契约、检查脚本、台账一律只读。
- 公开接口只按 SPEC 增加；不改、不删原有的，不给 SPEC 没写的枚举加成员。
- 依赖、系统函数、真实数据、能启动的进程，照工单与波次规则，不自行扩大。
- 测试只放在工单指定的文件里，测试名与数量和工单完全一致；不许 `#[ignore]`、过滤或拆分凑数。

## 3. 自己做决定，不要停下等许可

下面五种情况，执行者自己做下去，回执里写清楚，总控验收时逐条看：

1. **旧断言要跟着改。**
   - 因本单改动而必然要变的旧断言，直接迁移到新值。回执逐条写：原值 → 新值 → 为什么必然要变。
   - 迁移后的断言不能比原来弱：原来核对精确值的，不能改成只核对“存在”或“大于零”。
   - 工单已经预列“获准修改”的，照预列做；没预列但必然要变的，同样照这条做。
2. **计时失败。**
   - 只因超时、`took N ms` 这类计时断言失败的，原样重跑，最多 3 次，回执记一句。
   - 计时失败**永远不是受阻理由**。重跑 3 次仍只因计时失败，照常交回，回执写明是哪条断言、几次、各多少毫秒，由总控判断。
   - 不要自己调大时限、删计时断言或改检查器。
3. **两种做法都符合工单时**，选更保守的那个做下去，回执写明另一种是什么、为什么没选。“更保守”指：删得更少、动的文件更少、不加新接口、用户看到的变化更小。
4. **工具或环境的小障碍**（缺一个命令行工具、某种查看方式用不了、路径写法不对），工单写了替代办法就照做；没写就用最接近的等价办法，回执记录。例如设计稿不能在浏览器里打开时，读 HTML 源码与预览截图。
5. **工单与代码对不上的小处**（行号偏了、函数改了名），按工单要达到的行为做，回执写明对照。

## 4. 只有这几种情况才受阻

- 要删测试，或要降低断言强度（见第 3 节第 1 条）；
- 要改白名单以外的文件，包括别的单的文件、契约、检查脚本、台账；
- 要改公开接口、依赖、系统函数，或扩大真实数据的读取范围；
- 工单与 SPEC 或契约互相矛盾，照哪一边做都会违反另一边；
- baseline 失败，或工作树状态不对；
- 非计时类的失败，原样重跑仍失败、而且不是本单代码造成的（例如检查器自己报错）。

受阻回执写清：冲突在哪、试过什么、需要总控补什么（最小补充）。不要自行变通。

## 5. 夹具与真实数据

- 合成夹具只能建在本树 `.local/` 下：每次用随机名新建一个目录，测试结束**只删除本次新建的那一个目录**（校验父目录与名字前缀），不得递归删除任何别的东西。工单另有例外的照工单。
- 测试的隔离根一律在本树 `.local/` 下，**不得**在任何盘根建 `.water-quarantine`。
- 真实数据一律只读，范围照波次规则与工单；输出只有计数或组级汇总，不含路径与名字。

## 6. 检查与负控

- 模式照波次规则（`lock`、`check`、`test`、`browser`、`real`、`native`、`red-ncN`、`archive`）。
- 负控只改生产代码里真正被调用的那一处，不改测试、不加开关；跑 `--mode red-ncN` 以目标标记失败；**立即** `git checkout -- <文件>` 恢复原字节，再跑一次 `test`（界面单浏览器负控跑 `browser`）变绿。
- 用编译错误、超时或改测试造出来的红不算数；别的测试先失败的也不算数，换更窄的位置。
- 新断言的失败信息要带工单给的标记；不要只靠共用的辅助函数报错，那样失败信息里没有标记。
- 工单要求测试某个检查时，测试要走到产品代码里真正调用它的地方；只测抽出来的小函数不算覆盖。确实走不到的（没有可插手的时机、要两个真实盘），回执写明原因，不要写成“已覆盖”。

## 7. 收尾与回执

1. 实现与测试全部提交，得到干净的实现提交；在它上面依次跑工单列出的 final，再跑 `archive`。
2. 回执与证据逐个文件 `git add` 后单独提交；证据里被忽略的 `.log`、`.png` 用 `git add -f`。
3. 回执第一行与给用户的通知完全一样：`<单号> 任务已完成，任务报告在 <绝对路径>`；受阻写“任务受阻”。
4. 回执写清：实际模型；实现提交 SHA；逐条对照工单；每个检查命令与结果；计时重跑（第 3 节第 2 条）；负控；迁移过的旧断言（第 3 节第 1 条）；自己做的选择（第 3 节第 3～5 条）；真实冒烟结果；界面单的截图差异；没做或没验证的事。
5. 回执用 UTF-8 写（例如 Node 的 `writeFileSync(..., 'utf8')`），不要经过会按系统代码页转码的管道或重定向。提交前读回整份，确认没有连续问号，也没有替换字符 `U+FFFD`。

**提交身份**：不许改 git 配置。只在提交命令的进程里设 `GIT_AUTHOR_NAME`、`GIT_AUTHOR_EMAIL`、`GIT_COMMITTER_NAME`、`GIT_COMMITTER_EMAIL`，用执行者自己的名字（如模型名）与 `<名字>@localhost`。不要借用仓库里已有的人类作者身份。

**远端与历史**：
- 不 push 到任何远端，不添加或修改 git 远端与配置；
- 不改写已有提交（不 amend、reset、squash、rebase 或任何强制操作），只在首次 HEAD 之后新增提交；
- 提交信息写错就在回执里说明，不要改写。

禁止：merge、`git add -A`、`git clean`、`git stash`、改主线台账、提交别人的文件。交回后停止一切测试与后台进程（包括无头浏览器）。
