## 要做的（全部在 `apps/water/ui/`）

### 1. 排空的组不能因为重读而回到清理范围（中）

**问题**：一个组仍在 `selection` 里、但可清理条目都被排除时，界面按“未选”显示（补单 02 第 3.1 条）。是否已选是拿“排除数 < 可清理数”判断的；重读后可清理数变大，这个组就自己变回已选，新恢复的那一项进了清理范围。

**例子**（新服务开关下的回放数据）：
1. Node 依赖目录有 i-000201、i-000202 可清理，i-000203、i-000204 已跳过。
2. 用户勾上这一组，在抽屉里把两项都取消。组显示为未选，抽屉提示“先在结果页勾选这个分组”。
3. 到“位置”恢复 i-000203 的跳过。
4. 重读后这一组变回已选（半选），操作坞多出 1 组、1 项、668 MB，`clean_prepare` 带上这一组，服务会删 i-000203。

“先取消 B，再对 A 点以后都跳过，再恢复 A”也一样。

**改为**：
- 一个组的可清理条目被全部排除时，就把它从 `selection` 里去掉，或者在重读前记下“当时未选”的组、重读后仍保持未选，做法你定。
- 要重新纳入，只能在结果页勾选这一组；现有规则会从“没有排除”开始。
- 组仍有部分条目被选中时，恢复的项按补单 03 处理：算进这一组，操作坞跟着变。

### 2. 低级

1. **跳过失败的提示会盖住后来的错误**：`skipFailure` 只在点关闭、下一次跳过、新扫描时清掉。之后 `clean_prepare` 失败（stale、busy、invalid）时，提示条仍显示“跳过没有成功……”；如果是 stale，结果页的“结果已过期”横幅也因 `errorCode === 'stale'` 被压掉，页面上没有任何说明。改为：后来的错误优先显示；或者在新错误到来、一次清理开始或完成时清掉 `skipFailure`。结果过期时，过期说明一定要看得到。
2. **每次勾选条目都把抽屉关掉再打开**：会重放滑入动画、重建遮罩、焦点先跳到抽屉后面的按钮再跳回来，读屏软件会重新播报。改为原地更新抽屉内容，不关不开。保留现有的滚动与焦点保持；条目被禁用后焦点要落在可见位置。
3. **恢复成功的措辞**：恢复的路径在本次结果里不一定有对应的项。把措辞改成不作这个断言，例如“已恢复，这个文件夹以后会照常体检”。具体措辞你定，不用 emoji。
4. **假宿主与真实服务对齐**（总控补单 03 写错的地方）：
   - 真实服务跳过或恢复时，只改这些：组的 `eligible_count` / `eligible_bytes`、组的 `by_drive` 可清理量、`summary_zh`、`selectable` / `default_selected`；该项在详情里的状态；推荐组的 `totals.recommended_bytes` 与 `recommended_by_drive`（零字节行不显示）。
   - 分类的 `total_bytes` 是各组总量之和，跳过后**不变**。假宿主照此改，“live skip replaces category totals”那条断言随之改；回执写原文。
   - 假宿主的 `skip_remove` 遇到不存在的 ID 返回 `not_found`；每次新增的跳过要有不同的 `skip_id`。
5. **模型里的保护与抽屉一致**：`setItemSelected` 判断组是否仍有选中项时，与抽屉一样带上保留的排除元数据（`selectionDetails`），不只看当前抽屉的 `data`。
6. **切换分类开关后也重读结果**：位置页切换某一类的开关成功后，按补单 03 同样的规则（同一 `scan_id`、保留选择、清空详情缓存、重读完成前不能清理、失败则过期）重读 `scan_result`。服务会把关掉的分类下的组改为不可选，`clean_prepare` 也会拒绝它们；现在操作坞会多算，点清理才报错。
7. **测试加强**：
   - 保持滚动的那条断言要先确认抽屉确实滚动过（滚动值大于 0），否则不算证明；
   - 重读后详情缓存被清空，要有浏览器层面能区分的断言，不能只靠每次打开都重新读取。
