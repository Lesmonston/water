## 2. 写代码

- **只改工单白名单里的文件。** 别的票正在改的目录一律只读：
  - G1 只改 `packages/junk-clean/`；
  - G2 只改 `packages/water-service/`；
  - G3 只改 `apps/water/ui/`；
  - `apps/water/host/` 属于正在进行的 F3。
- 契约、检查脚本、台账也不能改。契约冲突或缺东西时写受阻回执，不要自行变通。
- **公开接口不变**。G1 的公开 API 与 CLEAN 第 2 节相同，G2 的公开 API 与 SERVICE 第 2 节相同，G3 的 IPC 调用与 UI 契约相同。别的票与宿主都按这些接口编译。
- Rust：
  - 依赖不变，锁文件已存在，不要改 `Cargo.toml` 的依赖；
  - 全部离线；
  - 系统调用只写在 `src/native_windows.rs`，写法同第二波；
  - G1 允许的系统函数以 SPEC 列表为准，检查器会逐个核对。
- 生产代码不得启动进程、联网、读环境变量。
- 测试只放在工单指定的测试文件，测试名与工单完全一致，不许 `#[ignore]`、过滤或拆分凑数。

## 3. 夹具与真实数据

- 合成夹具只能建在本树 `.local/` 下工单指定的目录里：
  - 每次用随机名新建一个目录；
  - 测试结束**只删除本次新建的那一个目录**（校验父目录与名字前缀）；
  - 不得递归删除任何别的东西。
- G1、G2 的删除测试只在夹具里删除，计划里不得出现任何真实用户位置。
- 用户已授权开发期对本机做**只读**扫描。本波唯一的真实读取是 G2 的 `--mode real`（清理保持关闭，输出不含路径或命令行）。G1、G3 不读真实位置。
- 原生窗口 0、选择框 0。G3 的浏览器测试只开一个私有 headless Chrome。

## 4. 检查与负控

| 模式 | 作用 |
|---|---|
| `lock` | G1、G2：锁文件已存在，只核对依赖 |
| `check` | 依赖与源码政策、`cargo fmt --check`、`cargo clippy -D warnings`；G3 为语法检查与界面政策 |
| `test` | 跑工单指定的测试（G3 为单元测试），名字与数量必须完全一致 |
| `browser` | G3 的浏览器测试与截图 |
| `real` | G2 只读真实冒烟 |
| `red-nc1` 等 | 有效负控 |
| `archive` | 把 `.local/checks/<票号>/` 的回执、日志与截图按原字节复制进证据目录并写索引 |

负控做法：
1. 只改生产代码里真正被调用的那一处，不改测试、不加开关；
2. 运行 `--mode red-ncN`，它必须以目标失败信息失败；
3. **立即**用 `git checkout -- <文件>` 恢复原字节，跑一次 `--mode test` 变绿，再做下一条。

检查器会核对源码哈希。用编译错误、超时或改测试造出的红不算数。G3 的 nc2、nc3 由检查器跑浏览器测试证明，恢复后仍跑 `--mode test`。

**机器上同时有几张票在编译与测试**，磁盘可能很忙。服务的 50 ms 返回预算若因此超时一次，可以原样重跑一次 `--mode test`，并在回执里如实写明；连续两次超时就停下写受阻回执。

## 5. 收尾

1. 实现、测试（与 G3 的样式、脚本）全部提交，得到干净的实现提交。
2. 在这个干净提交上依次跑工单列出的 final。final 会核对负控记录；产品字节不变时不要重复跑。
3. 跑 `--mode archive`，写回执（路径见工单），把回执与证据目录逐个文件 `git add` 后单独提交。后续提交只能含回执与证据。证据里的 `.log` 若被忽略，用 `git add -f`。
4. 回执第一行与给用户的通知完全一样：`<票号> 任务已完成，任务报告在 <绝对路径>`；受阻则写“任务受阻”。
5. 回执必须写清：
   - 实际模型；
   - 实现提交 SHA；
   - 逐条对照 SPEC；
   - 每个检查命令与结果；
   - 负控：改了哪一处、失败信息、恢复后的哈希；
   - G2 的真实冒烟摘要；G3 逐张截图写看到了什么；
   - 没做或没验证的事。

禁止：push、merge、rebase、`git add -A`、`git clean`、`git reset --hard`、`git stash`、改主线台账、提交别人的文件。交回后停止一切测试与后台进程。
