## 对 Water 开发的启发

（按盘累积，C 盘部分）

1. **认出了却不让清**：Codex 插件市场升级残留每份都带 `.git`，被“这是代码仓库”的保护拦下，229 份一份都清不了。规则需要能声明“这类目录里的 `.git` 是下载副本，不是用户仓库”。
2. **Chromium 分区缓存没覆盖**：“桌面应用网页缓存”只认 `<应用>\Cache`；微信开发者工具（4.1 GB）、QQ、Steam、WeGame 这类 `Partitions\<分区>\Cache` 或自带内核的缓存不在规则里。
3. **泄漏要按模式提示**：“每 15 分钟一份”“每棵工作树一份”这种同类目录成批出现、持续增长，比按大小排序更能找到根源；Water 现在要等多次体检才有增长提示，且看不到簇。
4. **记录摘要不准**：清理记录写“清理 26 组，跳过 71 项”，但只有 20 组真删了东西，3 项失败也没写。
5. **确认前应算出实际可清的量**：浏览器开着时整组都会跳过，确认框写 17.9 GB、实际 12.0 GB；应在确认前按当前在用情况给出预计值，或提示先关浏览器。
6. **桌面应用缓存没有在用检查**：Claude 桌面版开着时，它的 `Cache`、`Code Cache` 被删了（这次没看到问题，但规则的在用方式是“无”）。
7. **字节口径**：界面按 1024 进制、写作 GB，与资源管理器一致；总控的报表也应用同一口径，否则用户会以为数字不对。
8. **核对计划的办法好用**：“清理所选”后、永久删除前，计划已落盘，总控能逐组核对用户勾选，两次都抓到了偏差。可以考虑在确认框里直接列出按组的项数与在用跳过数。
9. **“工具给每个账号做的用户主目录”要能进去看**：Water 把整个“Grok 其它账号目录”当成一块受保护数据，里面 1.46 GB 的 npm 缓存它看不见。这类目录（Grok 的 `.grokN`、Mirasim 的 `home`、Antigravity 的实例目录）里同时有会话、浏览器登录配置和普通缓存，规则应能进去按常规规则认出缓存，同时保护会话与登录。
10. **会话记录的保留规则值得告诉用户**：Claude Code 默认删除 30 天前的会话，用户并不知道。Water 在“会话记录”一组里可以写明各工具自己的保留规则，以及单个超大会话（这次一个 4.1 GB）。
    - **`denglou` 总控的分析**（`F:\new\denglou\worktrees\ui-v2\docs\ops\SESSION-COMPOSITION-ANALYSIS-20261102.md`，11-02）按 `Read` 的路径补全了原因：读图片 4,015 次、1,167 MB，其中 55% 是同一张截图再读一遍；截图多是模拟器 1080×2400 的全分辨率 PNG；文字文件只有 16 MB。它定的改法：截图先缩成 JPEG 再看（实测降到 1/15～1/30）、能用文字验证的不看图、一张图只看一次、一份交接开一个新会话（最后一条要用户操作）。
    - **它给 Water 的产品线索**：对**已结束**的 agent 会话做“瘦身”，剥离图片 base64 与 `toolUseResult` 里的重复副本、保留文字，这一个会话约可回收 1.8 GB。边界：只动已结束的会话、先备份、瘦身后续接那个会话看不到当时的图。这值得排进 Water 以后的计划（会话记录现在是只统计不清理）。
11. **应用会建出资源管理器删不掉的名字**：剪映的 `DeflickerCache `（结尾带空格）。Water 的执行器用长路径删除，能处理；但用户自己删、或总控脚本用普通 PowerShell 遍历时都会失败。Water 遇到这类名字可以单独提示。
12. **“最近 7 天改动”不等于“最近 7 天新增”**：一直追加写入的文件（会话记录、数据库、日志）整份计入，总控据此向用户报了偏大的“新增”。Water 的“近 7 天新增”若按修改时间算，也会有同样的偏差；要说增长，应按两次体检之间的体量差。

14. **可识别的“软件更新”类垃圾**：没装上的更新包（QQ 的 `versions\<新版本>.zip`，`config.json` 的 `curVersion` 不是它）、保留的旧版本目录（夸克 `<旧版本号>`）、装好软件后留下的 `.rar`/`.zip` 安装包与解压出的安装程序。Water 现在只认识几种桌面更新器，这些都没有规则。

25. **整棵工作树能不能清，要看三件事**：分支是否已在远端、已跟踪文件有没有改动、未跟踪的文件在别处有没有副本。第三件要按内容找，不能只按同路径：F3 的 7 棵自检树按同路径比对时主线一个都没有，按内容哈希找，6 棵早已归档在别的目录，只有 `w2-selftest` 的 144 个文件确实只此一份。Water 的“Git 工作树”规则如果以后要建议清理整棵树，这三项就是判断依据，未跟踪文件的去向只能提示、交给人决定。
26. **在用检测要认各种路径写法**（11-02 清 `denglou`）：Git Bash、Node 起的进程，命令行里同一个路径写成 `F:/new/x` 或 `/f/new/x`。总控的隔离脚本原来只比反斜杠写法，三种都漏，当场改了；Water 的进程扫描会把 `/` 换成 `\`，`F:/…` 能认，`/f/…` 认不出，已排进第九波 L4。
27. **另一个 agent 正在工作的项目，“在用”不只是程序路径**：清 `denglou` 时，它的总控正在另一个会话里做真机测试，4 个 PostgreSQL 的数据目录、模拟器、服务器脚本和日志都在 `_ctl` 下。命令行能看出数据目录（`-D …`）与日志重定向目标，所以要把这些目录整体当作在用；工作树里只动两天以上没改过的东西。
28. **泄漏目录里可能混着真东西**：`fix-r9\.tmp_w35b` 里除了 `verify-*` 泄漏，还有执行方的脚本、报告和数据库快照。所以要按模板挑成员，不能把父目录整个端走；模板还要严，`verify-` 后面正好 6 位字母数字，才不会把同目录的 `verify-s8-revisions.cjs` 当成泄漏。
29. **分级表到执行时会变**：回执写完不到一小时，A3 的 12 个测试包里有 3 个名字不是提交号（`apk_F1`、`apk_F2`、`apk_diag`），`.tmp_w35b` 实有 255 个而不是报告里写的 130 个，模拟器换了启动参数还在运行。执行前要按规则重新生成清单、逐条重查前提，不能照抄分级表的数字。
30. **压缩归档要先验后移**：每个 zip 先写成临时名，重新打开、核对每个文件的名字与大小、跑一遍校验码，通过才改成正式名；原目录核对通过后才进隔离，由用户删除。被别处当作出处记录的路径（`content` 工作树的导入记录 JSON 写着 `_review/zhenti/…`），在原位置留一份索引说明去向。
31. **“只留一份”之前先看谁在读**：项目外的 `F:\new\登楼知识库` 被出题脚本按路径读取，重复时永远留它那份。Water 以后做“重复文件”提示时，被项目引用的那份要排在前面，这又需要项目声明（`.water-cleanup.json` 的 `protected`）。
32. **联接让“在用”跨目录传递，这次差点出事**：`denglou` 的工作树普遍用联接共用 `ui-v2` 的 `node_modules` 与 `android`。被移走的 `grok2`（已脱离 git）里，`server\node_modules` 是指向 `ui-v2` 的联接；而保留下来的整合树 `audit-b57a`，它的 `server\node_modules` 又指向 `grok2\server\node_modules`。移走 `grok2` 就断了整合树的依赖。总控移完全盘查“还有没有联接指向被移走的路径”才发现，当场把 `grok2` 移回原位。教训：
    - **动一个目录之前，要先找“指向它的联接”**。有别的保留目录经联接用着它，它就是在用；进程检测看不到这种依赖。
    - **隔离目录里的联接要先拆掉，再让用户删**。这次隔离区里有 26 个联接，大多指向还在用的 `ui-v2`。删除命令若顺着联接进去，就会删掉在用的依赖。总控逐个确认是重解析点后做不递归的删除，只去掉联接本身。
    - Water 的执行器本来就不跟联接、逐级按文件 ID 核对，不受影响；但“目录被别处的联接引用”应该算作在用，规则与扫描都还没考虑，排进第十波。
33. **Python 3.10 的 `os.path.islink` 不认联接**：总控的压缩脚本靠它跳过链接，`_review\zhenti\final` 里一个指向 `content` 工作树 `node_modules` 的联接，会被当成普通目录走进去。这次是年龄门槛碰巧挡下了它（联接后面的缓存昨天刚写过）。修法：看文件属性里的“重解析点”标记。Node 的 `isSymbolicLink()`、GNU find 都把联接当链接，三者口径不一，写清理脚本时要统一按属性判断。
34. **给用户的删除命令默认带 `\\?\` 前缀**：11-02 用户删 `denglou` 隔离区，`rd /s /q` 删完 167 GB 后留下一个文件 `worktrees\ui\nul`（3.3 MB，07-13 建）。`nul` 是设备保留名，按普通路径删不掉；常见来源是在 Git Bash 里照 cmd 的习惯写了 `2>nul`，bash 就建了一个真文件。11-01 C 盘留下的是名字结尾带空格的文件夹，属于同一类。两次都要加 `\\?\` 前缀才删得掉。
    - Water 的执行器按父目录句柄加单段名打开子项（`packages/junk-clean/src/native_windows.rs` 的 `nt_open_at`），这类名字不影响；计划里的路径本身含保留名则直接拒收（`path.rs`）。但“子项是保留名”没有测试，排进第十波 W10-M4。
    - 总控的隔离脚本移的是整个目录（同盘改名），不受影响。
    - **PowerShell 读不出这种文件的属性**：总控用 `Get-Item '\\?\…\nul'` 查，大小、时间、属性全是空的，就照着记成了“0 字节”。`denglou` 总控回执指出它实为 3.3 MB 后，用 node 经 `\\?\` 复核更正。核对保留名文件用 node 或 `cmd`；空值不能当作 0。
    - 交给用户之前先扫保留名：`precheck-plan.cjs --handover` 列出来，并给出带前缀的命令（`denglou` 回执 3.4）。
35. **挪之前查入向联接，别等挪完再查**（`denglou` 回执 3.1）：第 32 条是移完才查出 `grok2` 链，靠当场移回补救。现在把它前移成生成计划时的闸（`precheck-plan.cjs --plan` 的 `IN`）：全盘不跟随联接地找“指向候选的联接”，把链解到最终目标，在执行单里写“X 改指 Y 后再清”，交所属项目总控改指。在真实现场试跑：假设要挪 `ui-v2\server\node_modules`，它查出 11 棵工作树的联接都指向它。
36. **“脱离 git”不等于“没用”**（`denglou` 回执 3.2）：B1 的理由是“成果都已在中央库”，只对 git 跟踪的内容成立。`yb-release\.tmp_local_build` 是被 git 忽略的正式签名副本，总控没查出来，它已随隔离区删除。商店签名在 EAS，少的是一份本机离线备份（见执行单“收尾回执”）。
    - git 查不到的价值有两种：被在用的目录经联接依赖（第 35 条），以及被 git 忽略的贵重件（签名、证书、私钥、`.env*`、`credentials*`、本机数据库）。
    - 清脱离目录前按文件名扫一遍（`precheck-plan.cjs` 的 `KEEP`），只列名、不打开，交所属项目总控判断。输出存到计划旁边，删除前留有文件级的底；隔离日志只记到目录一级。
    - 请别的项目总控出分级回执时，每行要写“git 忽略的贵重件：无 / 有”。
    - 对 Water：候选目录里有这类文件名时，不能列为“推荐”；卡片列出文件名，交项目判断（排进第十波）。
37. **延后项写明解除条件和谁来收尾**（`denglou` 回执 3.3）：这次 `grok2`（某联接改指后）、`climbmao_a35` 快照（模拟器关机后）都写了原因和条件，`denglou` 总控收尾时不用重新判断，转去知会后几分钟就开始收尾。执行结果表固定加这一栏，收尾方填完回执。对 Water：跳过的项写明“关掉 X 后可清”。
